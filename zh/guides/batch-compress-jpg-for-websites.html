网站工作流指南

网站批量压缩 JPG：尺寸、命名与核心网页指标

网站图片常在两个方向出错：像素远多于显示尺寸，或者细节远多于字节能承载。批量流程先确定显示宽度，再按宽度和字节预算压缩每张图，两头都能解决。

快速回答

先确定图片占用的 CSS 宽度，按约两倍宽度导出以兼顾高密度屏，再把每张 JPG 压到 100KB 到 300KB。760 像素正文栏约需 1520 像素，360 像素卡片约需 720 像素。同时在 HTML 里写宽高属性，避免加载时布局跳动。

从布局宽度出发，而不是相机分辨率

现代相机输出 4000 像素，是因为要保留裁剪和打印的细节。网站在 360 到 1200 CSS 像素宽的栏里显示它。直接提供相机文件会浪费带宽，还可能推迟最大内容绘制，在手机上尤其明显。因此批量流程的第一个决定是显示宽度，而不是压缩质量。

如果只提供一个文件，并且要在普通屏和高密度屏上都清楚，按约两倍 CSS 宽度导出。760 像素正文栏用 1520 像素图；360 像素卡片用 720 像素。如果能提供响应式来源，窄屏用更小文件更好；但一个尺寸合适的文件，已经比 4000 像素原图好很多。

图片重量与 Core Web Vitals

Google 的核心网页指标包含三个字段指标：LCP 衡量加载，INP 衡量响应，CLS 衡量视觉稳定。图片直接影响 LCP，当头图或首篇文章图是视口内最大元素时；缺少预留空间时也会造成 CLS。只有当图片确实是 LCP 元素时，减小文件才对这个指标有帮助；压缩装饰图仍能节省带宽，但不会移动该指标。

CLS 是布局问题，不是压缩问题。给图片加上与内在宽高比一致的 width 和 height 属性，或在 CSS 里设置明确的 aspect-ratio。浏览器就能在图片到达前预留空间。压缩无法弥补缺失的预留。

INP 关乎交互延迟。大图在滚动或输入时可能竞争主线程解码时间，低端手机上尤其明显，但更大的收益通常来自 JavaScript。即便如此，提供 200KB 而不是 4MB 的图片，能减少解码工作和内存压力。

可重复的批量流程

  1. 列出图片及位置。记录 CSS 宽度、是装饰图还是 LCP 候选、是否需要透明度。
  2. 按选定宽度导出。裁剪到预期宽高比，避免 CSS 不可预测地裁剪。
  3. 为每个位置定字节预算。用上表作为起点，而不是规则。细节商品图可能需要更多，柔和背景可能更少。
  4. 在首页批量压缩。加入全部 JPG，选择目标预设，运行“全部压缩”，检查每个文件的原大小和新大小。
  5. 重命名输出。使用描述性、小写、连字符文件名，例如 kitchen-remodel-card.jpg。提供多个尺寸时把宽度写进名字。
  6. 每种位置抽检一张。发布前把最小和最大的文件都在 100% 下打开。
  7. 在 CMS 里补宽高和 alt。压缩和无障碍是两件事，上传时一起做完。

命名、缓存与重新压缩

图片 URL 是缓存键。替换文件但保留同名，某些缓存和 CDN 可能继续提供旧字节。图片变化时使用内容哈希或版本后缀，或配置主机正确失效。描述性名字也有助于图片搜索，并让半年后的资源文件夹仍然可读。

需要新尺寸时，不要对已发布的 JPEG 再压一遍。回到原始导出，缩到新宽度，一次编码。反复打开保存已发布文件会累积伪影，甚至在同质量下产生更大文件。

网页交付中的其他格式

JPEG 仍是照片风险最低的选择。WebP 常以更小体积提供相近画质，当前浏览器广泛支持；AVIF 可能更小，但编码和支持程度不一。生成 WebP 或 AVIF 时保留 JPEG 回退，并测试实际返回的 content type。标志、图表和文字通常用 PNG 或 SVG 更好，无论字节大小，因为锐利边缘能保留，透明度也不会丢。

批量决策不是“全部压到 20KB”，而是“按每个位置需要的尺寸和格式交付”。

没有构建系统也能做响应式图片

静态网站仍可用 srcset 和 sizes 提供合适尺寸。导出两三个宽度，统一命名，让浏览器按视口和像素密度选择。这比一个文件麻烦，但能避免把 1520 像素图发给 360 像素手机。维护不了多个宽度时，正文内容用一张 1200 像素图是合理折中。

把现代格式当增强，而不是硬要求。picture 元素可以先提供 WebP 或 AVIF，再提供 JPEG 回退。测试现代格式不可用时回退是否生效，并确认服务器返回正确 content type。把 WebP 错标成 image/jpeg，即使浏览器支持该格式，也可能在某些客户端失败。

测量结果，不要假设

发布后，检查浏览器实际下载的字节数，以及真实页面加载中的 LCP 元素。被 CMS 缩略图挡住的压缩成果可能根本到不了访客。用网络面板或分析工具的 Web Vitals 数据确认哪张图是 LCP 候选、它有多大。如果页面仍加载 2MB 原图，批量工作就没有生效。

还要在慢速网络和小屏幕上检查。桌面快速连接下瞬间出现的头图，可能在手机上主导 LCP。为窄视口提供更小的候选文件，往往是单项最有效的改动。

常见问题

1200 像素头图用 100KB 够吗？

100KB 在 1200 像素宽时约 0.55 位/像素，会发软。用 200KB 到 500KB 或现代格式，并在实际显示尺寸下测试。头图常是 LCP 元素，文件大小重要，但可见损伤比稍大的文件更糟。

能用 CSS 缩小大图代替压缩文件吗？

不能。CSS 改变显示尺寸，浏览器仍会下载完整文件。上传前要缩小资源本身。

压缩会删除 alt 文本吗？

alt 文本在 HTML 里，不在图片文件里。重新编码不影响它，但上传新文件可能需要在 CMS 里重新填写。
