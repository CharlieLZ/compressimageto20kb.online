Upload rules guide

JPG upload size limits: 20KB, 20,000 bytes and totals

Most upload failures come from reading a limit as a single number when the form enforces several at once. This guide separates the byte convention, the per-file cap, the total cap and the dimension rule, then gives you a calculator for the combination.

Updated 14 November 20267 min readCalculator runs locally

Quick answer

A 20KB limit usually means 20,480 bytes, but some portals mean 20,000. A per-file limit does not guarantee a total limit, and a size limit does not replace a dimension rule. Aim 5–10% below the stated cap, check the exact byte count, and calculate the total before uploading several files.

Four limits that hide behind one sentence

A form might say “Upload a photo, maximum 20KB.” In practice the server can enforce any of the following: a maximum number of bytes per file, a maximum total number of bytes for the request, a minimum and maximum pixel dimension, a required aspect ratio, and an allowed MIME type. Passing one check does not imply passing the others. The fastest way to avoid a loop of rejections is to write all stated constraints down before touching the image.

There is also a difference between what the interface says and what the server measures. A browser file picker may display “20KB” while the server compares the raw byte length of the uploaded part. Some servers include multipart boundaries and headers in the request size, which can add a few hundred bytes. That is why a file sitting exactly on the limit is fragile and a file 5–10% below it is not.

KB, kB and bytes

Strictly, kB means 1,000 bytes and KiB means 1,024 bytes. Consumer software rarely respects that distinction. Image tools usually display binary kilobytes, so 20KB means 20,480 bytes. Network and storage interfaces sometimes use decimal units, so 20KB means 20,000 bytes. The 480-byte difference is small in absolute terms but decisive at a hard boundary.

Per-file limits versus total limits

A per-file limit caps each image independently. A total limit caps the sum of all files in the submission. Portals that accept a photo plus a signature plus a certificate often enforce both: “each file up to 100KB, total up to 250KB.” If you optimise each file to exactly 100KB, the total fails. The correct approach is to divide the total budget first, then compress each file to its share.

Filenames, form fields and encoding overhead also consume space in some implementations. Base64 encoding, used by email and some APIs, adds roughly 33% to the binary size. A 100KB image becomes about 133KB of text before headers. Understanding which transport applies prevents a file that passes a local size check from failing after encoding.

Dimension rules are separate

A 20KB file can be 200×200 or 2000×2000. The byte limit says nothing about whether the face is large enough, whether the image is square, or whether the minimum resolution is met. Identity and application portals commonly require 600×600 pixels, 2×2 inches at 300 DPI, or a specific aspect ratio. Compressing first and discovering the dimension rule later wastes an upload.

When a form states both a size and a dimension, check whether they are compatible. A 600×600 photo at 20KB is about 0.46 bits per pixel, which is extremely aggressive for a face. If the form also demands 20KB, it is effectively asking for a low-detail image. If it allows 100KB, the same dimensions are comfortable. The combination, not either number alone, determines whether the result will look acceptable.

Reading rejection messages correctly

  • “File exceeds maximum size.” Reduce bytes. Check decimal versus binary and re-check the exact properties.
  • “Image dimensions too small.” Increase pixels. This conflicts with a tight byte cap; crop rather than lowering quality further.
  • “Image dimensions too large.” Resize down. Do not merely lower JPEG quality; the server checks width and height.
  • “Invalid file type.” Check the actual encoding, not the extension. A PNG renamed to .jpg is still a PNG.
  • “Total upload too large.” Recalculate the combined budget, not each file in isolation.
  • “Unexpected error.” Often a server-side size check before validation. Try a file 10% smaller to test the hypothesis.

A safe default strategy

For an unknown portal, prepare a 600-pixel-wide JPEG at roughly 70–80% of the stated byte cap. That combination passes most dimension and size checks and still looks like a photograph. Keep the original high-resolution file. If the portal rejects the dimensions, you can re-crop from the original rather than re-compressing a compressed copy. If it rejects the size, you have margin to go smaller without another generation of loss.

For multi-file submissions, calculate the total first, assign a per-file budget, compress to 90% of each share, then verify the sum. This is slower than compressing everything to the stated per-file maximum, but it avoids the most common total-limit failure.

Server checks you cannot see

A form can validate the file in the browser and again on the server. The browser check may use the reported file size; the server check may count the entire request body, including headers and other fields. Some servers also decompress or transcode the image before storing it, then enforce a limit on the stored version. That is why the same file can pass one portal and fail another with an apparently identical rule.

There is no reliable way to inspect those checks from the outside. The practical response is margin: stay 5–10% below the stated cap, avoid exactly-at-the-limit files, and retry with a clearly smaller file if an unexplained rejection occurs. If a portal rejects a file that is far below the limit, the cause is usually dimensions, format or a total-request cap rather than bytes.

ZIP files and combined uploads

A ZIP archive is convenient but not a compression shortcut for JPEGs. The images are already compressed, so the archive mainly bundles them and adds a small amount of metadata. A 5MB folder of JPEGs may become a 4.9MB ZIP. If the portal counts the archive against a total limit, zipping does not create meaningful headroom; you still need to reduce the images themselves.

Some portals reject archives entirely, or accept them but do not preview the contents. Read the upload instructions before bundling. If individual files are required, submit them individually and keep the total under the cap.

Frequently asked questions

Does the browser file picker show exact bytes?

Not usually. Operating systems display rounded sizes. Open the file’s properties or use the compressor’s reported byte count when the limit is strict.

Can I upload a JPG with a different extension?

The server usually inspects the file signature, not just the name. Renaming does not convert the format and can trigger a security rejection.

Why does the same file pass on one portal and fail on another?

Different servers, different byte conventions, different request overhead and different dimension rules. Treat each portal as its own contract.
