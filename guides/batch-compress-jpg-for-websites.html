Website workflow guide

Batch compress JPGs for a website

Website images fail in two directions: too many pixels for their display size, or too few bits for the detail they show. A batch workflow fixes both by deciding the display width first, then compressing every image to that width and a sensible byte budget.

Updated 14 November 20268 min readBatch tool on the homepage

Quick answer

Decide the CSS width each image will occupy, export at roughly twice that width for high-density screens, and compress each JPG to 100–300KB. A 760-pixel article column needs about 1520 pixels; a 360-pixel card needs about 720. Keep width and height attributes so the layout does not shift while images load.

Start from layout width, not camera resolution

A modern camera produces 4000-pixel images because it captures detail for cropping and printing. A website displays them in a column that may be 360 to 1200 CSS pixels wide. Serving the camera file wastes bandwidth and can delay the largest contentful paint, especially on a phone. The first decision in a batch workflow is therefore the display width, not the compression quality.

For a single file that must look sharp on both standard and high-density screens, export at about twice the CSS width. A 760-pixel article column gets a 1520-pixel image; a 360-pixel card gets 720 pixels. If you can serve responsive sources, smaller files for narrow screens are better, but one well-sized file is already a large improvement over a 4000-pixel original.

Why image weight matters for Core Web Vitals

Google’s Core Web Vitals use three field metrics: LCP for loading, INP for responsiveness and CLS for visual stability. Images affect LCP directly when the hero or first article image is the largest element in the viewport, and affect CLS when they lack reserved space. A smaller file helps LCP only if the image is actually the LCP element; compressing decorative images is still useful for bandwidth but does not move that metric.

CLS is a layout problem, not a compression problem. Add width and height attributes that match the intrinsic aspect ratio, or set an explicit aspect-ratio in CSS. The browser can then reserve space before the image arrives. Compression cannot compensate for a missing reservation.

INP is about interaction latency. Large images can compete for main-thread decode time during scrolling or input, especially on low-end phones, but the bigger wins usually come from JavaScript. Still, serving a 200KB image instead of a 4MB one reduces decode work and memory pressure.

A repeatable batch workflow

  1. List the images and their placements. Note the CSS width, whether the image is decorative or the LCP candidate, and whether it needs transparency.
  2. Export each image at the chosen width. Crop to the intended aspect ratio so CSS does not have to crop unpredictably.
  3. Choose a byte budget per placement. Use the table above as a starting point, not a rule. A detailed product shot may need more; a soft background may need less.
  4. Batch compress on the homepage. Add all JPGs, select the target preset, run Compress All, and check the result table for each file’s original and new size.
  5. Rename the outputs. Use descriptive, lowercase, hyphenated names such as kitchen-remodel-card.jpg. Keep the target in the name if you serve multiple sizes.
  6. Verify one file per placement type. Open the smallest and the largest at 100% before publishing the batch.
  7. Add dimensions and alt text in the CMS. Compression and accessibility are separate chores; do both at upload time.

Naming, caching and re-compression

Image URLs are cache keys. If you replace a file but keep the same name, some caches and CDNs may continue serving the old bytes. Use a content hash or a version suffix when the image changes, or configure your host to invalidate correctly. Descriptive names also help image search and make a folder of assets intelligible six months later.

Do not re-compress an already published JPEG when a new size is needed. Go back to the original export, resize to the new width, and encode once. Repeatedly opening and saving a published file accumulates artefacts and can produce a larger file at worse quality.

Formats beyond JPG for web delivery

JPEG remains the lowest-risk choice for photographs. WebP often delivers similar quality at a smaller size and is supported by current browsers; AVIF can be smaller again but encoding and support vary. If you generate WebP or AVIF, keep a JPEG fallback and test the actual delivered content type. For logos, diagrams and text, PNG or SVG is usually better than JPEG regardless of byte size, because sharp edges survive and transparency is preserved.

The batch decision is not “compress everything to 20KB”. It is “serve each image at the size and format its placement needs”.

Responsive images without a build system

A static site can still serve appropriate sizes with the srcset and sizes attributes. Export two or three widths, name them consistently, and let the browser choose based on viewport and pixel density. This is more work than one file, but it avoids sending a 1520-pixel image to a 360-pixel phone. If you cannot maintain multiple widths, a single 1200-pixel image is a reasonable compromise for article content.

Use modern formats as an enhancement, not a requirement. A picture element can offer WebP or AVIF first and a JPEG fallback second. Test that the fallback works when the modern format is unavailable, and confirm the server sends the correct content type. A mislabelled WebP served as image/jpeg can fail in some clients even when the browser supports the format.

Measure the result, do not assume it

After publishing, check the actual bytes the browser downloads and the LCP element in a real page load. A compression win that is hidden behind a CMS-generated thumbnail may not reach the visitor. Use the network panel or your analytics’ Web Vitals data to confirm which image is the LCP candidate and how large it is. If the page still loads a 2MB original, the batch work did not take effect.

Also check a slow connection and a small screen. A hero that looks instant on a desktop with a fast connection can dominate LCP on a phone. Serving a smaller candidate for narrow viewports is often the single most effective change.

Frequently asked questions

Is 100KB enough for a hero image?

For a 1200-pixel-wide hero, 100KB is about 0.55 bits per pixel and will look soft. Use 200–500KB or a modern format, and test at the actual display size. A hero is usually the LCP element, so file size matters, but visible damage is worse than a slightly larger file.

Should I use CSS to shrink large images instead of resizing files?

No. CSS changes display size but the browser still downloads the full file. Resize the asset before upload.

Does compression remove alt text?

Alt text lives in the HTML, not the image file. Re-encoding does not affect it, but uploading a new file may require re-entering alt text in the CMS.
